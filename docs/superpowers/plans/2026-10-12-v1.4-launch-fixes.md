# CleanFeed v1.4 — Launch Fixes Plan

**Goal:** make CleanFeed reliable enough to market. Fix the 1 critical and the high-severity bugs from the 2026-10-11 audit, plus a few very visible quick wins. Hide three low-demand features instead of fixing them. Bump to v1.4.0.

**Spec / evidence:** `research/bug-audit-2026-10-11-details.json` → `findings[N]` (title, file, line, trigger, cause, fix_hint, verifier notes) and the Italian summary in `research/bug-audit-2026-10-11.md`. Each task lists the finding indexes it owns. Read those entries for evidence. Where the task text below differs from a finding's fix_hint, **the task text wins**.

**Branch:** `fix/v1.4-launch-fixes`, starting from baseline commit `851fb22` (the snapshot of the v1.3.2 working tree). Never commit to `main`. Never push.

## Global Constraints

1. Plain-JavaScript Manifest V3 extension: no build step and no new runtime dependencies. If the extension loads a new file, add it to `manifest.json` (content scripts) or to the matching HTML or `importScripts`, AND to the `package.sh` whitelist.
2. Never put untrusted data (titles, channel names, keywords, search queries, imported JSON) into `innerHTML` or `insertAdjacentHTML`. Build DOM with the existing `cfEl` helper or `textContent`.
3. Every new user-visible string is English-first. Add the key to BOTH `_locales/en/messages.json` and `_locales/it/messages.json`, and read it through the project's message helpers (`msg()` in content.js and options.js, `cfMsg()` in popup.js). A literal `$` before a digit must be written `$$`.
4. Stay inside the task's scope. Follow the existing style (2-space indent, existing helpers, existing naming). Don't refactor unrelated code.
5. Verification on every task:
   - `node --check` on every modified `.js` file.
   - Pure-logic changes get unit tests under `tests/unit/*.test.js`, run with `node tests/run-unit.js`, which must exit 0.
   - DOM/YouTube-dependent changes are verified with the live harness `tests/live/` (Task 1) when the task says so.
   - Put the commands and their output in your report.
6. Commit once per task (more commits are fine) on the branch, with a conventional message (`fix: …`, `feat: …`, `chore: …`, `test: …`) ending with the line `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.
7. Existing users' stored data must keep working. No destructive migrations. Read old shapes defensively.
8. Do not modify `lib/ExtPay.js`.
9. `tests/` is dev-only. It must never be added to `package.sh`.

### Task 2: 3-dot menu injection freezes the tab; stale card blocks the wrong channel

**Findings:** #0 (critical), #35.

**Problem:**
- `injectBlockOption` (content.js) early-returns only when `existingItem.dataset.cfChannel === channelName`.
- When the card has no detectable channel name (channel-page videos, homepage Shorts, ads), no item carries `data-cf-channel`. The function then removes and re-inserts its items on every call.
- The MutationObserver in `watchForMenuPopup` sees those mutations and calls it again: an infinite microtask loop that freezes the tab.
- Separately, `lastClickedVideoCard` is never cleared, so a menu opened outside any card (e.g. under the main video) can get "Block channel permanently" for a previously clicked card.

**Required behavior:**
- Injection is idempotent for the same popup and the same card. A second call with nothing changed must not mutate the DOM.
  - Use a sentinel that is always set, e.g. a per-card token stored on the injected items, and compare against it.
- The injector's own DOM changes must never re-trigger injection in a loop. Disconnect the observer during injection, or ignore self-caused mutations.
- `lastClickedVideoCard` is set on every menu-button click: to the card, or `null` when the click is outside any card. Injection only happens for a popup opened shortly after a click inside a card (about 1 second; use a timestamp).
  - If the click was outside a card, remove any stale CleanFeed items from the popup and inject nothing.
- Cards without a channel name still get the "Not interested in this topic" item, once.

**Verify:**
- Unit-test any pure helper you extract.
- Live: add `tests/live/menu.js`:
  - Open `https://www.youtube.com/@mkbhd/videos` (logged out).
  - Click a video card's 3-dot menu button.
  - Confirm the page stays responsive (`page.evaluate(() => 1)` resolves within 3 s, repeated a few times over ~5 s).
  - Confirm exactly one set of CleanFeed menu items exists in the open popup.
  - Do the same on a search results page.
- Run it BEFORE the fix to record the failure (RED), and after (GREEN).

### Task 3: Read only the visible page, not YouTube's hidden cached pages

**Findings:** #11, #14, #49, #37.

**Problem:**
- YouTube keeps previously visited pages in the DOM, hidden: `ytd-browse[hidden]` and `ytd-watch-flexy[hidden]` under `ytd-page-manager`.
- Document-wide `querySelector` calls therefore read hidden pages, which causes four bugs:
  - `YT.getPageChannelName` / `getPageChannelId` return the hidden watch page's channel owner on a channel page, so Block, Peek and the blocked check hit the wrong channel.
  - `YT.isChannelPage()` stays true on home/search after visiting a channel.
  - The blocked-channel page handling (content.js around line 823) hides the wrong container and leaves its banner on other pages.
  - The subscriptions toast re-scans hidden cached cards and reappears after every navigation.

**Required behavior:**
- Add one helper in content-dom.js, e.g. `YT.getActivePageRoot()`. It returns the currently visible page element (the `ytd-page-manager` child without `hidden`), falling back to `document`.
- Page-level lookups use it: page channel name and id, channel-page detection, blocked-channel page container and banner, and the subscription-exception scan.
- `isChannelPage()` uses the URL check plus only a *visible* channel header or browse page.
- On SPA navigation (`onNavigate`), remove the blocked-channel banner and undo the blocked-page state from the previous page.
- The subscriptions toast must not repeat for the same keyword+channel pair within a session (keep a session Set).
- Card-level filtering of hidden pages may keep running (cheap and harmless). Only the page-level decisions above must change.

**Verify:**
- Unit-test `isChannelPage`/`getActivePageRoot` with a stub DOM if practical; otherwise live only.
- Live: add `tests/live/navigation.js`. Open a watch page, then SPA-navigate to a channel page by clicking the owner link, and check:
  - `YT.getPageChannelName()` returns the channel page's name (evaluate inside the content-script world, or check the effect, e.g. the Block button's target).
  - After navigating to home, `isChannelPage()` is false and no blocked-channel banner exists.
- Document what you could and couldn't observe.

### Task 4: Keyword matching engine — Unicode words, exact synonym blocking, no everyday-word synonyms

**Findings:** #10, #9, #47, #48.

**Required behavior:**
1. **Unicode-aware matching.** `matchesKeyword(text, keyword)` must treat letters and digits from any script as word characters:
   - Use lookarounds such as `(?<![\p{L}\p{N}_])…(?![\p{L}\p{N}_])` with the `u` flag.
   - Case-insensitive.
   - Normalize both sides with NFC, and normalize typographic apostrophes (’ ‘ ʼ) to `'`.
   - Do NOT strip diacritics. "citta" must not match "città" (avoids false positives such as Spanish año/ano).
   - Keywords that start or end with a symbol (e.g. `c++`, `f1`) must still match at their natural edges.
   - Multi-word keywords keep the current flexible-spacing behavior if any exists.
2. **Exact synonym blocking.** `getExpandedKeywords(keyword)` expands ONLY when `keyword` (lowercased) equals a category key in `KEYWORD_SYNONYMS`. Blocking a word that merely appears in a category's synonym list blocks just that word.
   - Category exemptions (`isCategoryExempt`) apply only to category blocks.
   - Custom synonyms added under a category still expand with that category.
   - Check every caller of `getExpandedKeywords` in content.js; any that assumed reverse expansion must use the new semantics.
3. **Remove everyday-word synonyms.** Delete standalone ambiguous terms or replace them with unambiguous phrases. Take the full list from findings #47 and #48 (e.g. `persona`→`persona 5`, `forza`→`forza horizon`, `partita` removed, `destra`/`sinistra` removed, `tea`→`spill the tea`, `beef`→`youtuber beef`, `twice`→`twice kpop`, `cristiano` removed, `slot`→`slot machine`, `stake`→`stake casino`, `paura` removed, `trucco` removed, plus any others the findings name).
   - Don't add new categories.
   - Keep each category's intent.

**Verify:** unit tests (write them first, see them fail, then fix):
- `matchesKeyword('Attualità e politica', 'attualità') === true`
- `matchesKeyword('Tour della città di Roma', 'città') === true`
- `matchesKeyword('Обзор игры', 'игры') === true`
- `matchesKeyword('Learning C++ fast', 'c++') === true`
- `matchesKeyword('display', 'play') === false`
- `matchesKeyword('Baldur’s Gate 3', "baldur's gate") === true`
- `getExpandedKeywords('minecraft')` does not include `'fortnite'`
- `getExpandedKeywords('gaming')` includes `'minecraft'`
- None of the removed everyday words remain as standalone synonyms.

### Task 6: CF+ quick-add and Scan produce keywords that actually match

**Findings:** #4, #31.

**Problem:**
- The quick-add popover tokenizer (content.js around 3130–3230) deletes every character outside `[a-z accented-latin 0-9]` *inside* words: "Baldur's" → "baldurs", "Spider-Man" → "spiderman".
- The Scan tokenizer (around 2375) deletes apostrophes ("dell'anno" → "dellanno").
- The saved keyword then never matches the title.
- Non-Latin titles offer no chips at all.

**Required behavior:**
- Tokens keep their internal characters. Only leading/trailing punctuation is trimmed, using a Unicode-aware definition (`\p{L}\p{N}`).
- Italian/French elisions split at the apostrophe (`dell'anno` → `dell'`, `anno`, or just `anno` as the useful token). The phrase `dell'anno` must still match the title via `matchesKeyword`.
- Non-Latin words produce chips.
- **Safety net:** before saving any selected phrase from CF+ or Scan, check it with `matchesKeyword(sourceTitle, phrase)` for CF+ (or against at least one analyzed title for Scan). Skip phrases that fail, and log/skip quietly.
- Keep stop-word filtering behavior as-is otherwise.

**Verify:**
- Extract the tokenizers into pure functions (in content.js, or in content-dom.js if shared) so they can be unit-tested via the loader.
- Unit tests:
  - Chips for `"Baldur's Gate 3 – Spider-Man: l'ultimo dell'anno"` include `baldur's`, `spider-man`, `anno`.
  - Every chip phrase matches the original title.
  - Cyrillic titles produce chips.

### Task 7: Auto-tag only for topics, count each video once, untag sticks

**Findings:** #1, #8, #19.

**Required behavior:**
1. **Topics only.** Category hits are queued, and tagged channels checked, only when the matched blocked keyword is a topic (a `KEYWORD_SYNONYMS` category key, via `canonicalCategoryOf` or equivalent). Plain custom keywords (e.g. `trailer`) never auto-tag channels.
2. **Count each video once.** One video counts at most once per category per channel:
   - Within a page session: dedupe by video id, else title+channel; skip outer wrappers that contain another card.
   - Across sessions where feasible: background stores a capped set of counted video ids per category+channel (cap e.g. 20 ids each) so revisiting the same video doesn't add hits.
   - The threshold stays 3 distinct videos.
3. **Untag sticks.** "Untag channel" records the channel in a per-category exclusion list (new storage key, default `{}`). `batchIncrementCategoryHits` never auto-tags excluded channels again.
4. **Visible and reversible.** Options → the Blocked/topics area shows, per blocked topic, the channels auto-tagged for it, each with an Untag button that uses the same exclusion path.
   - New i18n strings in en+it.
   - Keep it simple: a list under the category's existing accordion content.

**Verify:**
- Unit-test the background/storage counting logic. Factor it into a pure function if needed, load `storage.js` in a vm with a fake `chrome.storage.local`, or test a pure helper.
- Cases:
  - 3 hits from the same video id → not tagged.
  - 3 distinct videos → tagged.
  - Untagged channel + 3 more distinct videos → still not tagged.
  - Plain keyword → no hits queued (test the content-side predicate as a pure function).

### Task 11: Strict Mode really locks

**Findings:** #2, #5.

**Required behavior:**
- **Background enforcement.** When `settings.strictModeEnabled` is true, `background.js` rejects every *weakening* action unless the request carries a correct `strictPassword` (verify against the stored hash exactly as `verifyStrictPassword` does). - **Popup and Options.** On `strict_locked`, prompt once for the password (reuse the options page's existing prompt pattern; add the same to the popup), then retry the action with `strictPassword`.

  - A wrong password shows the existing error string.
- **On-page controls.** While strict mode is on, these are hidden or disabled, with a localized tooltip/label like "Locked by Strict Mode": the on-page pause toggle, Peek, Untag and the 'Hide More relevant' toggle.
  - Do not collect passwords inside YouTube pages.
  - The page reacts live to the setting via `onStorageChanged`.
- **Import.** A backup that would disable strict mode or remove blocks is a weakening action and needs the password.

**Verify:**
